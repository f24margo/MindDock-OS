НАЙДЕНО И ИСПРАВЛЕНО (2 бага в новом engine.py/strategies/gaussian_mm.py):

1. Bug: котировки пересчитывались от ТЕКУЩЕЙ цены тика прямо перед
   проверкой пересечения на ТОМ ЖЕ тике — математически исключало любой
   fill (bid всегда строго ниже price-в-этот-момент по построению).
   Давало 0 trades при любом max_order_age. Fix: котировка выставляется
   один раз и стоит неизменной до следующего пересчёта/филла, проверка
   пересечения — на следующих тиках.

2. Bug (sign error в inventory skew): старая формула
   bid = price*(1-spread-skew), ask = price*(1+spread+skew) сдвигала
   bid и ask в ПРОТИВОПОЛОЖНЫХ направлениях. При position<0 (шорт) это
   давало skew<0, из-за чего ASK приближался к цене (наращивание шорта
   становилось привлекательнее) вместо того чтобы отдаляться (что
   снизило бы риск). При spread=0.05%/skew=0.10 это давало Total PnL
   -0.108704 на ~14000 trades — канал мог инвертироваться (ask<bid).
   Fix: skew теперь сдвигает общий reference_price (в духе Avellaneda-
   Stoikov reservation price), спред остаётся симметричным вокруг него.
   После фикса AvgInv упал на порядок (с ~0.35-0.53 до ~0.01-0.02 при
   skew>0) — skew теперь реально удерживает инвентарь, не разгоняет его.

КАЛИБРОВКА max_order_age: на реальных тиках (1000PEPEUSDT, 2.77
тик/сек в среднем) при spread=0.3% нужен max_order_age в диапазоне
300-1000+ тиков, чтобы котировка успевала "отстать" от цены и дать
шанс на fill. age=10-100 (3.6-36 сек) систематически дают 0 trades —
котировка переустанавливается быстрее, чем цена успевает уйти на
0.3%. Зафиксировано визуально через новый visualizer.py
(movement coridor vs price).

GRID SEARCH РЕЗУЛЬТАТЫ (один день, 2026-06-18, age=750 фиксирован):
- Широкий скан spread 0.05%-0.3% x skew 0-0.1: после фикса skew-бага
  Total PnL во всём диапазоне в пределах -0.000152...+0.000006 (на
  $100 notional) — практически ноль, без катастроф.
- Тонкая сетка spread 0.25%-0.5% x skew 0-0.02: лучшие результаты
  кластеруются у skew=0 на ВСЕХ уровнях spread (паттерн воспроизводится
  стабильно), но абсолютные числа (+0.000001...+0.000006) слишком малы
  и близки друг к другу, чтобы утверждать про оптимальный spread —
  похоже на шум одного дня, не статистически значимый сигнал.

ОГРАНИЧЕНИЯ ТЕКУЩЕЙ ВЕРСИИ (явно, чтобы не забыть):
- Один день данных = ОДНА реализация случайного процесса цены.
  Результаты grid search (особенно "spread=0.3% оптимален") НЕ
  валидированы на других днях/режимах рынка (тренд/флэт/высокая
  волатильность). Нужно несколько дней для статистической значимости.
- bookDepth используется со ступенчатой (conservative ceiling)
  интерполяцией между bucket'ами 0.20%/1.00% — спреды 0.3% и 0.6%
  оба попадают на bucket 1.00%, что огрубляет multi-level
  дифференциацию. Capped=0 во всех прогонах — текущий lot_size=0.01
  слишком мал, чтобы depth когда-либо стал узким местом; это НЕ
  проверяет реалистичность ограничения ликвидности при бОльших объёмах.
- Объём на bookDepth-уровне восстанавливается каждый тик (не убывает
  внутри 5-секундного окна между снэпшотами) — upper-bound на fill
  rate, не честная оценка. Не использовать для решений о реальном
  размере позиции без дополнительной проверки.
- Multi-level котирование (buy_spreads[1]/sell_spreads[1] = второй
  уровень) ещё не подключено — используется только buy_spreads[0]/
  sell_spreads[0]. Решение из сессии: сначала валидировать одноуровневую
  версию, multi-level — следующий шаг.
